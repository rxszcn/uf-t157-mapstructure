# 宽表键匹配性能基准

## 背景

`decodeStructFromMap` 在精确键查找失败后，会退回到 `DecoderConfig.MatchName`
（默认 `strings.EqualFold`）逐键比较。原实现对**每个**未精确命中的字段遍历
**全部**映射键，因此宽表上的键/字段大小写不一致报文会退化为
O(字段数 × 键数)，四千字段宽表可达两百多毫秒，拖垮入库批次窗口。

优化后：默认 `strings.EqualFold` 语义下，首次回退时按 Unicode 折叠轨道
（`unicode.SimpleFold` 轨道最小元）为该 map 构建一次预索引，后续字段按
O(1) 桶查找，候选键再经 `strings.EqualFold` 复验，结果与原全键扫描逐字一致。
自定义 `MatchName`（非 `strings.EqualFold` 指针）仍走原有全键扫描，语义不变。

键数少于 `foldIndexMinKeys`（32）的小表仍走原线性扫描：小表上建索引比扫描更
贵，典型结构体的小表解码因此没有任何额外开销。

## 复现

```bash
# 宽度阶梯：250 / 500 / 1000 / 2000 / 4000
./scripts/bench-wide.sh

# 指定迭代次数与用例
BENCHTIME=10x BENCH='Benchmark_DecodeWide$' ./scripts/bench-wide.sh
```

三种输入键形态：

- `exact`：键与字段标签完全相同，走直接查找（基线）。
- `fold`：键与标签仅大小写不同，每个字段都走回退匹配。
- `miss`：键完全无法匹配，回退路径最坏情况。

`Benchmark_DecodeWideCustomMatchName/custom-fold` 使用自定义大小写不敏感
匹配函数，走原全键扫描路径，用于确认自定义匹配函数语义未被改变。

## 优化前后对照（ns/op）

环境：Intel Core i7-10700，Windows 11，`go1.27.4`，`-benchtime 10x`。

| 用例 | 优化前 | 优化后 | 倍数 |
| --- | ---: | ---: | ---: |
| exact/250 | 197,280 | 171,360 | 1.2x |
| fold/250 | 942,760 | 197,850 | 4.8x |
| miss/250 | 1,196,430 | 162,710 | 7.4x |
| exact/500 | 412,250 | 286,800 | 1.4x |
| fold/500 | 3,418,040 | 385,660 | 8.9x |
| miss/500 | 4,416,820 | 361,450 | 12.2x |
| exact/1000 | 749,110 | 608,080 | 1.2x |
| fold/1000 | 13,040,410 | 816,320 | 16.0x |
| miss/1000 | 18,178,150 | 711,870 | 25.5x |
| exact/2000 | 1,667,210 | 1,279,650 | 1.3x |
| fold/2000 | 53,863,330 | 1,918,930 | 28.1x |
| miss/2000 | 66,173,000 | 1,885,520 | 35.1x |
| exact/4000 | 3,691,020 | 3,962,730 | ~1.1x |
| fold/4000 | 237,060,360 | 3,946,480 | 60.1x |
| miss/4000 | 279,800,910 | 3,432,390 | 81.5x |
| custom-fold/4000 | 210,142,610 | 124,711,810 | 同路径 |

结论：

- `fold` / `miss` 由随宽度平方增长（250→4000 约 252x / 234x）变为线性增长
  （250→4000 约 20x / 21x），四千字段回退路径从 ~240ms 降到 ~3.9ms，
  与精确匹配（~4.0ms）同数量级。
- 未失配的 `exact` 路径无回退、不构建索引，读数在噪声范围内。
- `custom-fold` 优化前后走的是同一段全键扫描代码，两次读数差异属机器噪声；
  其仍随宽度平方增长，符合预期：自定义匹配函数不回退，语义原样保留。
- 全量既有基准（`Benchmark_Decode*`）在 32 键阈值下与优化前持平
  （交替采样中位数比值 0.90–0.92），小表解码无额外开销。
